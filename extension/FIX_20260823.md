# 修复记录：进度卡住、重复集数、并发异常等稳定性问题

修复时间：2026-08-23

## 问题现象（用户反馈）

- 下载时进度卡住，之后一直下载但下载的是重复集数
- 并发数异常（显示不正常），进度恢复后并发恢复
- 整体不稳定，各种小问题

## 根因分析

### 1. activeCount / inflight 内存态丢失（并发异常、重复派发核心原因）
- `activeCount` 和 `inflight` 是内存变量，Service Worker 被 Chrome 杀掉重启后丢失，重置为 0 / 空集合
- 重启后 `reconcileDownloads` 虽然会校正状态，但 `activeCount=0` 导致 `pump` 认为无进行中任务，立即派发新任务
- 此时 Chrome 下载管理器中仍有旧的 `downloading` 任务在跑，导致并发数 = 旧下载 + 新派发，超出限制，表现为并发异常
- 同时 `inflight` 为空，`pickBookDispatch` 的去重检查失效，同一集可能被重复派发，产生 `(1)` 副本

### 2. reconcileDownloads 长时间占用队列锁（进度卡住核心原因）
- 旧实现在 `withQueue` 锁内串行执行 `chrome.downloads.search({id})`，每个 track 一次
- 若任务有大量集数或下载查询慢，锁被占用数十秒，期间所有 `updateTrack` / `handleDownloadChanged` / `pump` 的存储更新都被阻塞
- 表现为：进度条不动、UI 无响应、并发数不更新，锁释放后进度突然恢复

### 3. 重复集数去重不完整
- 原去重仅检查其他任务中 `status===done` 的集，且在锁外检查，竞态下可能漏检
- 后端去重仅检查 `pending` 状态，已 `ack` 变为 `done` 后再次推送同一专辑会产生新任务，插件侧未拦截
- 同一专辑被推送两次，两个任务会同时下载相同集数，产生 `(1)` 文件

### 4. setTaskAndUpdateIndex 双写覆盖
- `autoApproveIfEnabled` / `pollBackend` 第二阶段 / `approveAndProcess` / `resumeAll` 等在 `withQueue` 内既修改了外层 `idx`，又调用 `setTaskAndUpdateIndex`（内部再次 `getIndex`+`setIndex`），最后再 `setIndex(idx)`，存在旧快照覆盖风险
- 虽然因锁串行化未直接导致数据丢失，但造成额外读写放大和潜在竞态

### 5. pendingTerminals 无界增长后直接 clear
- `pendingTerminals.size > 1000` 时直接 `clear()`，导致终端事件丢失，`runTrack` 的 `awaitTrackDone` 永远等待，直到 30 分钟超时才标记失败，期间槽位泄漏，进度卡住

### 6. getXmCookie 缓存未失效
- 冷却标记后缓存仍保留 5 分钟，导致插件继续尝试已被冷却的账号，限流错误反复出现

### 7. offscreen 文档重建不可靠
- `ensureOffscreen` 依赖 `offscreenReady` 内存标志，旧 Chrome 无 `hasDocument` 时文档崩溃后无法重建，导致官方源永久失败

### 8. 其他小问题
- `keepAlive` 周期 0.5 分钟被 Chrome 钳制到 1 分钟，且不可靠
- `buildFilename` 未限制长度，可能超 OS 路径限制
- `activeCount` 与 `inflight.size` 可能不一致

## 修复方案

### 核心重构
1. **移除 activeCount，统一使用 inflight.size**
   - `inflight` 为唯一并发计数来源，`pump` 循环条件改为 `inflight.size < limit`
   - `finally` 中删除 `inflight` 条目即自动减少并发，无需单独计数器

2. **reconcileDownloads 两阶段重构**
   - 阶段1：短锁快照需要检查的 track（`downloading`/`resolving`）
   - 阶段2：锁外执行 `chrome.downloads.search`，避免阻塞队列
   - 阶段3：短锁批量更新状态，并重建 `inflight`（将仍在 `in_progress` 的 track 加入 inflight）
   - 这样即使有大量 track，锁占用也仅为快照和批量写入，进度不再卡住

3. **inflight 重建与清理**
   - `reconcileDownloads` 重建 inflight
   - `handleDownloadChanged` 在 track 变为 `done`/`error` 时清理 inflight，防止 SW 重启后残留
   - `clearTasks` 删除任务时清理对应 inflight 条目
   - `cancelTask` 取消时清理

4. **重复去重增强**
   - `runTrack` 中去重检查改为：同专辑 + 同 track_id + 同格式，且状态非 `error` 的都算重复（包含 pending/resolving/downloading/done）
   - 增加锁内二次校验，防止并发派发竞态
   - `pollBackend` 拉取新任务时，本地检查是否已存在同专辑+同曲目集的任务（任何非 cancelled 状态），若存在则跳过并仍 ack 后端，避免反复拉取

5. **索引更新统一路径**
   - 新增 `upsertIndexEntry(idx, task)` 锁内更新索引条目，避免重复 `getIndex`
   - 所有 `withQueue` 内的更新改为：`getIndex` → `setTask` → `upsertIndexEntry` → `setIndex`，不再调用 `setTaskAndUpdateIndex`
   - `setTaskAndUpdateIndex` 保留仅供锁外调用

6. **pendingTerminals LRU 淘汰**
   - 超过 1000 时删除最旧 100 条，而非全部清空，避免终端事件丢失

7. **getXmCookie 缓存失效**
   - `markAccountCooldown` 后立即清空缓存，下次拉取最新可用账号

8. **ensureOffscreen 容错**
   - `hasDocument` 存在时以其为真相来源，不存在则重置标志重建
   - `getSign` 失败时重置 `offscreenReady=false` 并重试，最多 4 次，间隔递增

9. **keepAlive 修复**
   - 周期改为 1 分钟（Chrome 最小允许），增加心跳日志，`maybeStopKeepAlive` 改为检查 `inflight.size`

10. **buildFilename 截断**
    - 每段最大 80 字符，超长截断为 `...`，前缀 40 字符，避免路径过长

11. **其他**
    - `pumpQueued` 改为 `setTimeout(...,0)` 触发，避免同步递归栈过深
    - `runTrack` 增加锁内二次校验，防重复
    - `clearTasks` / `cancelTask` 同步清理 inflight

## 测试建议

- 多本书排队下载，concurrency=1，观察是否严格逐本下载，无并发超限
- SW 手动在 chrome://serviceworker-internals 停止后重启，观察是否恢复且无重复
- 推送同一专辑两次，观察第二次是否被去重，无 (1) 文件
- 模拟大量 track（1000+），观察 reconcile 期间进度是否卡住
- 官方源多账号轮询，标记冷却后是否立即切换
- 暂停/取消/重试链路是否正常，无复活已取消任务
